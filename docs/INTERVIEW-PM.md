# 面试话术 · AI 产品经理方向

> 项目：秋招求职台（个人单文件 Web 应用，上线 4 个在线节点，开源在 GitHub）
> 用法：先用「一、30 秒开场」定调，再按「二、演示动线」现场操作，最后用「四、追问应对」接招。

---

## 一、30 秒开场（背熟，不要展开技术细节）

> 我做的这个产品，起点是我自己求职时的真实痛点：牛客的校招日历不用登录就能看岗位，但**看完什么也留不下**——不能记录我投了哪些、走到哪一步、什么时候该跟进。
>
> 所以我做了一个「求职台」：**不用注册登录，打开就能用**，把「看岗位 → 记投递 → 跟进节点 → 复盘」这条链路闭环。它现在有 4 个在线页面，把校园招聘、央国企、本地实习分三个池子管理。
>
> 产品上的关键取舍是：**AI 能力全部走用户自带 Key（BYOK）**，我不承担任何推理成本，用户的数据也不出本机；同时保证**不配 Key 也能完整走通所有流程**，AI 只是加速器，不是前置条件。

**为什么这么定调**：PM 面试官最关心的不是「你用了什么模型」，而是**你怎么定义问题、怎么做取舍、怎么算账**。开场三句话分别落在这三件事上。

## 二、5 分钟演示动线（按用户旅程走，不按功能列表走）

| 步骤 | 操作 | 一句话讲什么 |
|---|---|---|
| 1 | 打开总览台 → 今日提醒 | 「用户打开就看到今天必须处理的事：快到截止的岗位、待确认的邮件通知、AI 挑出的推荐。**首页不是数据看板，是待办清单**。」 |
| 2 | 切到个人中心 → 简历档案 → 上传 Word 简历 → AI 解析 | 「简历是整个产品的数据源头——画像靠它、打分靠它。上传体验上我做了取舍：Word 直接在浏览器解析、零依赖、不上传服务器。」 |
| 3 | 秋招岗位台 → 筛选 → 挑一条 → 贴 JD → 打分 | 「岗位表我拿不到 JD 正文（牛客详情页是前端渲染），所以做了一键抓取的书签，用户在自己登录的浏览器里点一下就把 JD 送进剪贴板——**零反爬风险**。」 |
| 4 | 切「按匹配度」排序 → 点批量打分 | 「批量打分故意限制一次最多 8 条，执行前明确告知预估 token 消耗，且随时可中断。**花的是用户自己的钱，消耗必须透明、必须可控**。」 |
| 5 | 面试复盘 / 今日 AI 推荐 | 「复盘结果写回投递表形成闭环；推荐默认走本地规则排序，**零 token 成本**，想要 AI 理由再点，且当天缓存不重复花钱。」 |

**演示时的三条纪律**
1. 不打开代码，除非对方要
2. 每讲一个功能，先说「解决什么问题」，再说「怎么做的」
3. 主动暴露一个局限（如拿不到 JD 正文），再讲你的兜底方案——**这比完美更能体现产品判断**

## 三、PM 叙事主线（四个可展开的能力项）

### 1. 需求定义：从「别人的产品」里看到缺口
牛客校招日历是免登录的公开信息产品，验证了「聚合岗位」有需求；但它是**只读**的，用户看到岗位后没有任何沉淀。我的定位差异是「**把聚合信息变成个人进程管理**」——同一批岗位，一个是橱窗，一个是工作台。

### 2. 里程碑切分：M0–M6，每个都能独立交付
- M0 AI 设置面板 + 调用封装 → M1 简历档案 → M2 单岗打分 → M3 面试复盘 → M4 批量打分 → M5 智能推荐 → M6 邮件解析
- 切分原则：**每一步做完都能单独上线用**，不做「攒一个大版本再发布」。M1 做完就能传简历解析，M2 做完就能打分，用户（我自己）随时能用上增量。

### 3. 成本模型（PM 面试最加分的一块）
| 决策 | 理由 |
|---|---|
| 全站 BYOK | 我不承担推理成本，产品可以长期免费存活；用户为用量付费，动机一致 |
| 批量打分限 8 条 + 预估提示 + 可中断 | 一次性全表 600+ 岗位约 5 万 token，体验上是「黑盒烧钱」；限额让单次成本可预期 |
| 推荐默认本地规则排序（0 成本），AI 点评按需 + 当天缓存 | 高频场景不该依赖付费调用 |
| 开发与测试全程 Mock 模式 | 未配 Key 时返回演示数据，开发和自动化测试零额度消耗 |

**一句话总结**：「我没有把 AI 当卖点堆功能，而是把它放在**算得过来账的位置**上。」

### 4. 隐私架构（用户信任的产品设计）
- 云端数据只在作者账号可见；任何访客打开页面自动进**离线模式**，数据只存自己浏览器
- 不存在「服务器上堆着所有用户隐私」的情况——**因为产品架构里就没有这样一台服务器**
- 结果：我不需要承担数据托管的合规与运维责任，用户也不需要信任我

## 四、预期追问与应对

**Q1：这个产品的用户是谁？怎么增长？**
> 起点是我自己（求职者），同类人群特征很明确：同时盯多个招聘渠道、投递量大、节点多容易漏。增长上我不会走投放——这类工具的价值在**信任**，更适合求职社群、学长学姐推荐、开源社区传播。当前阶段我的目标是把它做成「一个人用也完全值得」的产品，而不是先做规模。

**Q2：为什么不做一个 SaaS，把所有数据集中起来？**
> 集中数据意味着我要承担隐私责任、服务器成本、合规风险，而收益只是「跨设备同步」这一个功能。我的判断是**这个交换不划算**，尤其对于求职这种高敏感数据（简历、面试记录、投递去向）。如果将来真要做同步，也应该先引入账号体系并重新设计隐私方案，而不是现在顺手把数据收上来。

**Q3：怎么衡量这个产品做得好不好？**
> 我自己的口径是三个：**① 漏投率**（有没有因为错过截止而丢机会）；**② 单次投递的准备时间**（找到匹配岗位 → 简历定向 → 记录投递，从多久降到多久）；**③ AI 功能的实际使用率**——如果某功能用户点了但不用结果，说明这个 AI 是伪需求，该砍。第三条我特别在意，因为 AI 功能最容易自嗨。

**Q4：市面上的求职工具很多，你的差异？**
> 两类竞品：一类是招聘平台自带的投递管理（只覆盖自家岗位），一类是通用表格模板（要自己维护）。我的差异是**跨渠道聚合 + 主动性**：不管是牛客、BOSS 还是官网投的，都汇聚到一个池子里；而且系统会**主动告诉你今天该干什么**，不是等你想起来才去查。这也是我把首页做成待办清单而不是数据看板的原因。

**Q5：如果让你继续做，下一个优先级？**
> 我会做「投递结果的归因分析」：现在系统知道投了什么、走到哪一步，但不知道**哪些简历版本、哪类 JD、什么时间点投递**的转化率更高。把这几个维度关联起来，就能从「记录工具」升级成「决策工具」——告诉用户「你投 AI 应用岗的转化率是算法岗的 2 倍」，这是真正的产品价值。
