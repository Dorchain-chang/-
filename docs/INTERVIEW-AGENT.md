# 面试话术 · Agent / LLM 应用工程师方向

> 项目：秋招求职台（纯前端单文件应用，6 个 AI 功能，BYOK 架构，在线 4 节点 + 开源）
> 本项目的定位：**一个把 LLM 调用工程化的完整样本**——统一网关、参数分层、Prompt 结构化、可观测、成本控制、降级兜底。

---

## 一、30 秒开场（技术密度要高）

> 这是一个纯前端的 LLM 应用：没有后端、没有服务器，六个 AI 功能（简历结构化解析、岗位匹配打分、面试复盘、投递画像、邮件解析、推荐点评）全部通过**用户自带的 API Key** 直连 OpenAI 兼容接口。
>
> 工程上我做了四件事：**① 统一调用网关**——所有功能走同一个 `aiChat()`，屏蔽服务商差异；**② 参数分层**——连接层、生成层、功能层解耦，每个功能的 temperature / max_tokens / System Prompt 都是可在页面上实时调整的参数；**③ 可观测**——每次调用记录功能、温度、耗时、返回长度、是否演示模式；**④ 降级兜底**——未配 Key 走 Mock、调用失败回落本地规则，页面永不白屏。

## 二、现场演示动线（3 分钟，专为技术面试官设计）

**演示 1：打开「Agent 调参台」（个人中心）**
> 「这是我把参数从硬编码抽出来的结果。左边选功能，中间是温度滑块和 max_tokens，下面是完整的 System Prompt。」
> 操作：选「岗位匹配打分」→ 看温度是 0.2 → 说明为什么。

**演示 2：现场改参数做 A/B 对比**
> 「同一段输入，我用当前参数和默认参数各跑一次，并排看差异。」
> 操作：输入一段 JD → 点「A/B 对比」→ 两侧输出并排显示，各自标注参数与耗时。

**演示 3：改 System Prompt 看行为变化**
> 「比如我在打分功能的 prompt 里加一句『输出必须包含一句反问面试官的问题』，输出结构立刻变化——**这就是 prompt 作为一等参数的价值：不用改代码就能调整 Agent 行为**。」

**演示 4：看调用记录**
> 「每次调用都落一条 trace：功能、温度、耗时、返回字符数、是否演示模式。这是成本和质量归因的基础。」

## 三、技术叙事（六个可深挖的点）

### 1. 统一网关：`aiChat(messages, opts)` 的抽象
```
调用点  →  aiChat()  →  [参数解析层]  →  fetch /chat/completions
              ↓
        aiCfg() 连接层：provider/base/key/model（本机存储）
        agTune() 生成层：temperature/max_tokens（功能级默认 + 用户覆盖）
```
**为什么要这层抽象**：6 个功能如果各自写 fetch，会出现「参数散落、错误处理重复、换服务商要改 6 处」的问题。收口成一个函数后，服务商切换、重试、trace 都只在一个地方实现。

### 2. 参数分层设计（这是最能体现工程判断的一点）
| 层 | 管什么 | 谁改 | 存哪 |
|---|---|---|---|
| 连接层 | provider / base URL / key / model | 用户配置一次 | `localStorage` |
| 生成层 | temperature / max_tokens | 用户按功能调 | `wb_agent_tune`（功能级覆盖，无记录=用默认） |
| 功能层 | System Prompt / 输入拼装 | 开发者或高级用户 | 同上 |

**关键设计**：`agTune(k)` 做的是「**默认值与用户覆盖的合并**」——用户没调过的功能完全走默认，行为完全可预测；调过的只覆盖该功能。这意味着加参数能力**不改变任何既有行为**，是零回归的增量。

### 3. 温度工程：为什么每个功能温度不同
| 功能 | 温度 | 理由 |
|---|---|---|
| 简历解析 / 邮件解析 | 0.2 | **结构化抽取**任务，输出必须是稳定 JSON；温度越高越容易格式漂移、字段缺失 |
| 岗位匹配打分 | 0.2 | 打分要**可复现可比较**——同一个岗位今天打 78 分、明天打 62 分，这个分数就没有决策价值 |
| 面试复盘 / 推荐点评 / 投递画像 | 0.4–0.5 | **表达与洞察类**任务，需要语言组织能力，温度过低会输出模板化、缺乏信息量的套话 |

**一句话**：「**判分和抽取用低温，讲故事和给建议用中温**——这是我按任务类型定的规则，现在做成了滑块让用户也能感知这个权衡。」

### 4. Prompt 结构化与防注入
- **结构化**：抽取类任务强制约束输出格式（「只输出一个 JSON 对象，不要输出任何其他文字」），再用 `/\\{[\\s\\S]*\\}/` 做**宽松解析**——容忍模型输出多余解释，提升鲁棒性
- **防注入**：输入用 XML 风格标签分段（`<简历内容>`、`<岗位JD>`、`<面试记录>`），把用户数据与指令隔离；同时在 system prompt 里明确「不得编造候选人未提及的经历」，约束模型不要被输入内容带偏

### 5. 可观测性（trace）
每次调用写入 `wb_ai_trace`（滚动保留最近 12 条）：功能、参数、耗时、返回字符数、是否 Mock。
**价值**：① 成本归因——哪个功能在烧 token 一目了然；② 质量排查——某个功能输出异常时先看输入长度和参数；③ 演示能力——面试/汇报时能指着记录说「这是真实调用链」。

### 6. 成本控制与降级
| 手段 | 实现 |
|---|---|
| 限额批量 | 批量打分一次最多 8 条，执行前告知预估 token，过程中可中断，剩余下次继续 |
| 缓存 | AI 推荐点评按天缓存，重复点击不重复请求 |
| 零成本默认路径 | 推荐默认走本地规则排序（匹配分 50% + 截止紧迫度 30% + 意向吻合 20%），不调模型 |
| Mock 降级 | 未配 Key → 返回带标注的演示数据，全流程可走通 |
| 调用失败降级 | 邮件解析等失败时静默回落关键词规则，不阻断写库 |
| 输入截断 | 简历/JD 按字符数截断（3000/6000），防止超长输入撑爆 token 与上下文 |

## 四、预期追问与应对

**Q1：为什么不做工具调用（function calling）或多轮规划？**
> 我评估过，这个场景的六个功能都是**单轮结构化任务**：输入明确、输出明确、不需要外部动作。引入工具调用只会增加延迟和不确定性，属于为了架构而架构。**判断标准是：任务是否存在「需要先决策再行动」的环节**——比如「帮我自动投递」就需要（要选岗位、填表、判断是否投过），而「给这个岗位打分」不需要。真正有 Agent 形态需求的是自动化投递，那涉及账号与合规，我不会在没有明确用户需求前做。

**Q2：没有记忆（memory）机制，算 Agent 吗？**
> 这个项目用的是**本机持久化作为记忆层**：简历档案、JD 缓存、打分结果、画像、复盘都存 localStorage，每次调用时作为上下文注入 prompt——本质上是「显式记忆」，由用户可见可控。我没有做「自动对话记忆摘要」，因为这是一个工具型应用而不是陪伴型对话，用户不需要它「记得我说过什么」，只需要它「读到我准备好的资料」。**记忆的设计要跟着产品形态走，不是越自动越好。**

**Q3：怎么评测（evaluation）效果？**
> 我目前用的是三层：**① 结构校验**——抽取类输出强制 JSON，解析失败即视为失败，可自动化统计；**② 参数对比**——调参台支持同一输入跑「当前参数 vs 默认参数」并排对比，人工判断哪个更好；**③ 业务侧验证**——我自己使用时的实际判断，比如打分是否「符合直觉、能解释」。
> 我知道更严格的做法是建标注集、算一致率（比如打分与人工评分做相关性），这也是我接下来想补的一环——**目前是「可对比、可复现、可归因」，但还没有量化的准确率指标**，这点我不夸大。

**Q4：为什么全做成前端调用，不走后端代理？**
> 因为**成本归属和数据边界**：走后端意味着我要承担所有人的推理费用并托管所有人的简历数据，风险与收益严重不匹配。BYOK + 前端直连后，Key 在用户本机、请求直连服务商、数据不经我手。
> 代价我也清楚：**Key 存在 localStorage 有 XSS 风险**，我的应对是①页面零第三方 JS 依赖 ②建议用户为这类工具单独建 Key 并设消费上限 ③提供「不记住 Key」的会话模式。这是当前约束下的合理取舍，不是不知道风险。

**Q5：LLM 接口的工程细节，你踩过什么坑？**
> 几个真实的：① **浏览器直连的 CORS**——不是所有服务商都允许浏览器发起请求，所以面板里必须给用户明确提示而不是静默失败；② **Mock 与真实的路径统一**——Mock 必须走同一个返回结构（Promise<string>），否则上层要写两套逻辑，我在网关层统一了出口；③ **输出解析的鲁棒性**——模型经常在 JSON 外面加解释文字，所以不能直接 `JSON.parse`，要先宽松提取再解析；④ **转义与构建约束**——这个项目是 Python 生成 HTML 的构建链，JS 字符串里出现会被 Python 解释的转义字符会直接破坏产物，我在构建链上加了守卫脚本（`check_escapes.py`）做静态拦截，而不是靠人眼检查。

## 五、一句话技术定位（收尾用）

> 「这个项目没有堆砌 Agent 概念，而是把 **LLM 应用工程化的基本功**做扎实了：统一的调用抽象、可解释的参数分层、按任务类型定的温度策略、结构化的 prompt 约束、可见的成本与调用记录、以及从 Mock 到规则的完整降级链路。我认为**能用简单架构解决的问题，不要用复杂架构**——这也是我对 Agent 工程的理解：能力要来自对任务的判断，而不是来自组件的堆叠。」
